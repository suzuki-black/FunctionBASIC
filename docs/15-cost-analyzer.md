# 15. 静的コスト・アナライザ（性能プロファイラ）

`src/analyze/cost.ts` は、FunctionBASIC ソースを **実行せずに** 解析し、各関数・ループ・ブロックの
推定実行コストを算出する静的プロファイラである。MSX 実機やエミュレータを使わずに「どこが遅いか（律速）」
を順位付けできる。CLI は `cost.mjs`。

## 15.1 なぜ必要か

MSX BASIC は 1 文ごとに実コスト（インタプリタのディスパッチ＋変数表の線形探索＋型処理）を持ち、
turbo R (R800) でも積もると律速になる。「物理演算をしていないのに 3〜4fps」という現象の正体は、
**毎フレーム約 10 関数・150〜200 文の解釈実行の総和**であって、単独の重い処理ではない。
実行時プロファイラ（TIME 差分の埋め込み）は計測自体がゲームを遅くし（浮動小数の加算が重い）、
値も汚す。静的解析ならコード構造から事前にコストを積算でき、この問題がない。

BASIC 専用の静的コストプロファイラは（調査した限り）他に存在しない。本ツールは gprof / Callgrind /
PL/SQL 階層プロファイラの定石（flat＝自己コスト順、hierarchical/tree＝呼び出し木の inclusive、
self と inclusive の区別、% 表示、hotspot 注記）を BASIC 向けに翻案したものである。

## 15.2 コストの単位と実機較正

すべてのコストは **「net TIME ティック / 2000 実行」** スケール。TIME は 60Hz なので、
1 回の実行の実時間 = `cost / 2000` ティック。毎フレーム合計 `/2000` = ティック/フレーム。
`fps ≒ 60 / (ティック/フレーム)`。

較正は `research/calib.msxb`（各操作を大ループで隔離し、エミュ内 `TIME` で計測）で行った。
**エミュ内 TIME はサイクル忠実＝ブラウザの実時間ジッタの影響を受けない**（msxpen で 5 回連続同値＝決定論的）。
実測値（turbo R / R800, net per 2000, base=13）:

| 操作 | net | 操作 | net | 操作 | net |
|---|---|---|---|---|---|
| 整数代入 | 24 | 実数代入 | 40 | PSET | 80 |
| 整数読み | 28 | 実数加算 | 70 | LINE | 140 |
| 整数加算 | 49 | 実数乗算 | 105 | **LINE…BF 16x16** | **300** |
| 整数乗算 | 54 | 実数除算 | 95 | LINE…BF 64x64 | 2620 |
| 整数除算(\\) | 61 | 文字列代入 | 32 | COPY | 180 |
| MOD | 63 | 文字列連結 | 73 | PUT SPRITE | 180 |
| AND | 51 | LEN | 47 | **GRP PRINT** | **320** |
| 配列1D読 | 45 | MID$ | 90 | PEEK | 37 |
| 配列1D書 | 41 | CHR$ | 52 | POKE | 42 |
| 配列2D読 | 66 | VAL | 63 | VPOKE | 62 |
| 配列2D書 | 61 | IF比較 | 50 | VPEEK | 69 |
| 関数呼び(引数0) | 34 | 関数呼び(引数1) | 67 | **RND** | **200** |

**重要な知見:**
- 関数呼びは安い（34）が、**引数 1 個ごとに +33**（引数渡しが高い）。
- **RND=200**（整数の約 10 倍）、**GRP PRINT=320**、**LINE…BF=300**、**PUT SPRITE=180** が突出。
- 整数演算・配列・関数呼び（引数少）は 24〜66 で安い。実数は整数の約 2〜3 倍。

## 15.3 コストモデル

`analyzeCost(program)` が AST を歩いて積算する。

- **式**: リテラル／変数読み（型別）／配列（1D/2D・添字式込み）／二項演算（整数・実数・文字列・比較で別重み）／
  組み込み関数（`BUILTIN_FN` 表）／ユーザ関数呼び（`callBase + 引数数×callPerArg + 呼び先 inclusive`）。
- **文**: 代入（LValue 書き＋右辺式）／組み込み文（`BUILTIN_STMT` 表。`LINE…BF` は塗り重み）／
  `IF`（テスト＋**重い方の枝**）／`FOR`（`反復数 × 本体`。反復数は CONST・単一定数代入グローバルを畳み込み、
  不明なら既定 8）／`WHILE`／`DO`／関数呼び。
- **インライン ASM**: `z80asm` が対応する命令のみ T-state 概算（`TSTATE` 表）で積算し、
  **後方分岐（DJNZ / JR cc / JP cc で手前ラベルへ）を検出してループ本体を倍化**する（DJNZ は直前の
  `LD B,定数` を反復数に使う。不明なら既定 16）。net スケールへは `K_ASM` で換算（ASM は BASIC より桁違いに安い）。
  **生 POKE でハンドアセンブルした機械語は解析対象外**（`POKE` 文として計上されるのみ）。
- **関数 inclusive**: 呼び先の本体を展開加算（再帰ガード・メモ化）。**self** は `inlineCalls=false` で
  呼び先本体を除いた自身のみ。

## 15.4 出力フォーマット

`cost.mjs`（CLI）は 2 ビュー:

1. **flat**（自己コスト順）: 各関数の `self`（自身のみ）と `incl`（子孫込み）。
2. **tree**（階層）: 関数／ループ／IF／ブロックを字下げ表示し、各ノードの inclusive ティックと
   親に対する % を出す。**突出ノード**（兄弟が 2 つ以上で親の 45% 以上）と**重い命令**（LINE 塗り・RND・
   GRP 出力・PUT SPRITE 等）に `◆` 注記。ループは `[xN]` で反復係数を表示。小さい枝は `… (N minor)` に集約。
3. **毎フレーム経路**: トップレベル `WHILE` をツリー化＝状態分岐（TITLE/PLAY/CLEAR/OVER）が分離表示され、
   `ST_PLAY` 枝の実コストだけを読める。

```
node --experimental-strip-types cost.mjs <file.msxb>            # flat＋毎フレーム木＋上位関数木
node --experimental-strip-types cost.mjs <file.msxb> --fn NAME  # 特定関数の木のみ
node --experimental-strip-types cost.mjs <file.msxb> --min 0.1  # 枝の表示閾値(tk)
```

## 15.5 限界（設計上の割り切り）

- **上限見積り**。`IF` は重い方の枝を常時実行、可変ループは既定反復数、稀にしか通らない重い枝
  （落下・掘り・当たり）も常時計上する。実測（orchard で毎フレーム ~15-20 tk）より予測（~44 tk）は高めに出る。
  → **絶対値でなく順位・相対で使う**。
- インライン ASM は概算（T-state 近似・反復数推定）。生 POKE 機械語は対象外。
- 変数表の位置による探索コスト差（先に参照した変数ほど速い）はモデル化していない（一律重み）。

## 15.6 応用: fps 予算

TIME 60Hz より、`20fps = 3 tk/frame ≒ 6000 net ≒ 整数 200 文`、`10fps = 6 tk ≒ 12000 net`。
毎フレーム経路の net を測れば「今何 fps 相当か」「目標 fps に何倍削減が要るか」を事前に出せる。
較正が示す設計則: **毎フレームに RND / LINE…BF / GRP PRINT / 多引数関数を置くな。整数演算・配列・
関数呼び（引数少）は安いので BASIC で書いてよい。** これは FAST ライブラリ（重い所だけ ASM）の線引きの根拠になる。
